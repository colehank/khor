## 2. 范围、阶段与完成标准

覆盖第一方 GUI、原生桥接、Rust 核心与节点、CLI/Web、Pi 与 ACP/A2A、网络与同步、构建发布、测试及维护文档。生成代码从生成器和类型来源审查；第三方代码审查适配边界与本地补丁。

| 阶段 | 工作 | 完成证据 |
| --- | --- | --- |
| P0 规划 | 对齐目标、边界、协作方式、首轮验收行为 | 用户决定有记录，提议与确认分开 |
| P1 全仓审计 | 建立模块清单；审查用户流程、状态、依赖、错误处理、测试与发布 | 每个模块都有已审查范围、证据、问题、未知项及后续任务 |
| P2 首批修复 | 复现键盘与提交跳转故障，检查同类滚动和焦点问题 | 回归先失败后通过，目标平台验收，说明旧测试漏检原因 |
| P3 逐模块重构 | 按风险治理 GUI、后端与协议边界，必要时替换模块实现 | 每批可独立构建、集成和回退，验证原有行为及声明的行为变化 |
| P4 工程治理 | 统一格式、命名、错误约定，整理测试入口、历史注释和失效代码 | 规则可重复检查，测试按功能可选择运行，文档与实际入口一致 |
| P5 整体验收 | 回归真实用户流程，核对问题清单与所有集成改动 | 选定范围闭环，未解决项明确，合并发布按本轮指令执行 |

P1 后确定 P3 的模块顺序和改造深度。格式规范在首批改动前确定，纯格式迁移单独成批。跨任务依赖显式记录，已知故障的最小修复无需等待所有模块重构。

按“影响、出现频率、波及范围、验证缺口”判断优先级并写出理由。函数长度、依赖数量、重复率用于定位候选。全仓模块记录“未审查 / 审查中 / 已审查 / 需复查”及对应提交，变更后按影响范围复查。

## 4. 多智能体分工

当前并发上限为四个：主智能体常驻，三个子智能体按阶段分工。角色随任务轮换；独立审查者不能是该改动作者。

| 阶段 | 主智能体 | 子智能体 A | 子智能体 B | 子智能体 C |
| --- | --- | --- | --- | --- |
| 审计 | 范围、依赖和跨模块边界 | GUI / 原生交互 | Rust / agent / 协议 | 测试、工具链、构建发布 |
| 实现 | 公共接口、集成与总账 | 一条独立功能链路 | 另一条不冲突链路 | 独立复现、审查与验收 |

主智能体负责用户对齐、任务分配、公共接口协调、集成、进度和交付判断。子智能体负责自己的任务卡、代码与证据；发现跨范围问题时提交证据和依赖请求。

派发必须包含：任务 ID、目标与完成标准、相关用户决定、基线提交、worktree、允许修改路径、依赖与接口约定、验证方式、交付位置。传递最小相关上下文；子智能体先核对实际文件与任务卡。

技术分歧通过最小复现、调用链和测试结果裁定，主智能体记录取舍；产品行为分歧交由用户选择。结论以代码与证据支持。

## 5. 隔离与集成

- 每个实现任务独立分支和 worktree，记录基线；只读审查可以共享固定提交。
- 主智能体维护集成分支与中央 STATE。子智能体维护自己的任务卡和授权路径；任一公共文件同一时间由一个任务负责修改。
- 治理的每次Cargo/native/生成器调用显式设置 `CARGO_TARGET_DIR=/Volumes/disk0/Khor/caches/rust/khor-quality-target`，按唯一槽串行（jobs1、incremental0）；不得因npm pregen漏环境而在worktree/target再建整套缓存。用户既有发布target不动。
- App、共享状态、公共 API、协议类型、生成器、依赖与锁文件、全局样式的修改先登记影响；接口先确定契约与兼容方式，再并行适配调用方。
- 文件不重叠也要检查语义依赖。依赖未完成接口时，先完成接口或明确兼容层。
- 子智能体交付提交、差异、测试和风险，主智能体逐个集成。冲突处理说明两边意图，重新验证受影响行为。
- 集成后验证针对确切版本；实现分支通过的结果仅适用于该分支当时的内容。
- 终端命令显式指定 worktree；开发服务器记录 PID、端口和目录。可写构建产物隔离，重编译与打包默认串行调度，按资源实测增加并行。
- 验证优先使用独立实例。用户会话与运行服务保留；清理只处理能确认归属的临时资源。

任务状态：proposed → ready → working → review → integrated → done。blocked / paused 另记原因与恢复条件。done 由主智能体按集成后的完成标准核定。子智能体退出不直接改变任务状态；发布状态另记。

## 7. 上下文压缩与恢复

在派发、关键判断、验证完成、交接、集成及结束一轮时更新记录。持续检查点使自动压缩发生时也有可恢复状态。

新会话、上下文压缩、智能体重启或接手任务后，依次执行：

1. 读取当前用户指令、AGENTS、协调目录内实时 STATE、PLAN 的执行规则和自己的任务卡；按任务读取设计与协议文档。
2. 核对工作目录、分支、HEAD、未提交差异、任务基线及产物路径。未提交代码以真实 diff 为准；缺失证据保持待验证。
3. 核对活动智能体和进程状态；接管前确认旧执行者已停止，更新所有者后再修改。
4. 比较测试记录对应的版本与当前内容。变化后评估影响并重跑相关检查，陈旧结果不能证明新版本正确。
5. 在任务卡写明恢复后的目标、最后确认事实、未证实假设和下一步，再执行。主智能体简短说明恢复到哪一步。

记录与现场不一致时保留现场并澄清差异。禁止仅凭压缩摘要覆盖代码、重复已完成的发布或清理来源不明的改动。

交接至少包含：任务 ID；所有者；worktree / 分支 / HEAD；未提交改动；确认事实；未证实假设；已排除方案及证据；检查及对应版本；尚缺验收；下一步；需保留的进程和产物；相关用户决定。

## 8. 验证与独立审查

故障修复先得到可重复失败证据，再修复验证。结构重构先确认需保持的行为与覆盖，再调整代码；低影响命名、格式调整使用适当静态检查。

验证覆盖纯逻辑、组件/浏览器交互、真实原生环境和集成用户流程。记录命令或步骤、环境、版本、结果和证据路径；存在未提交代码时，保存相关差异与新增源文件的内容指纹。模拟键盘、浏览器 WebKit、真实 iOS 键盘分别标明。交互在动画、焦点恢复、异步加载结束后检查最终状态，并覆盖连续操作。

审查者先依据需求与 diff 独立检查，再核对作者说明；检查状态归属、并发与取消、资源清理、兼容、错误处理和验证有效性。主智能体处理跨模块结论和集成顺序。

按项目要求运行既有门禁。新增或修改检查须能验证对应规则；已有失败记录基线、归属和影响。测试代码同样接受审查，避免只绑定函数名或源码形状。

2026-10-27执行补充：生成验证脚本使用独立命名STEP/TOTAL/MIN常数；launch前AST解析并核实际值，保存控制收据。来源/路径/precheck失败以check=True立即停止后续变更，禁止shell忽略错误继续。业务红、编译/setup、清理失败分开保原日志；共享target后续合法覆盖不回填历史binary收据。

关闭任务需要：目标达到；修改有归属；适用检查通过；独立审查完成；集成版本验证；所需真实 App 验收有记录；任务卡和 STATE 更新。里程碑交付问题变化、代码变化、证据、未解决项与下一批建议。
