## 已确认缺陷（固定源控制流；尚非生产现场故障）

### Q041-D01 · P1：镜像资产清单失败仍可能提交VERSION

`scripts/mirror-sync.sh:32–38`第二次curl API在`curl | grep | cut | while read`管道首部。POSIX sh没有pipefail；curl失败/JSON无browser_download_url时，末尾空while可exit0，set-e不阻止第37行写VERSION。第一次tag解析成功、第二次清单失败时，新VERSION与旧/空assets并存；后续同tag在29–30行早退，不会修复。初次tag为空有显式拒绝，这不能保护第二次请求。

独立轻量probe：`sh -c 'set -e; false | while IFS= read -r line; do :; done; printf would-advance-VERSION'`实际exit0，stdout为would-advance-VERSION。证明所用shell结构会吞上游失败；未运行mirror脚本，不把此probe当完整HTTP fixture红绿。

### Q041-D02 · P1：镜像不固定同一release，单文件atomic不等于整代一致

mirror-sync:20取latest tag、:26从main刷新installer、:32重新请求latest的assets、:34–35逐文件覆盖、最后写VERSION。两次latest之间新tag出现就可写“tag A、资产B”；任一中途下载失败可留一部分新asset、一部分旧asset。已有tag时installer还先从main更新，刻意不与release绑定；same-tag早退也不核缺项/摘要。固定`.tmp.<name>`、无互斥，还允许并发同步互踩stage文件。

`apps/site/deploy/push.sh:16–17`分两轮rsync，镜像同样没有线上整代提交；`Caddyfile`对/dl/*缓存300秒，客户端可各自命中不同代的固定文件名。此为条件明确的协议一致性缺口，未观察生产更新恰好撞到客户端。

**设计要求**：即使未来用“current目录symlink原子切换”仍不足：客户端分别GET二进制与sha时可横跨两次切换。必须先只解析一次release descriptor，然后使用不可变的release-id/tag目录URL取全部文件；descriptor/指针才原子提交。site推送必须保留这一目录/指针契约，不能在远端重新展开成平铺覆盖。

### Q041-D03 · P1/P2：安装入口核验契约不一致，镜像可忽略明确版本

`install.sh:54–62`镜像路径直接使用固定asset名，注释明确忽略KHOR_VERSION；而join.rs:316–324会明确传`v<caller version>`，形成“调用者要求vA、镜像实际装vB”且成功提示仍引用caller版本的条件缺陷。onset:243对镜像+显式tag反而拒绝，两个入口语义不同。

`install.sh:81–104`的网络下载与KHOR_ASSET_FILE仅gzip+4字节magic，未获取/消费release的.gz.sha256。合法gzip且ELF/Mach-O魔数正确的错误/被替换payload仍可原子替换binary。`join.rs:629–673`跨平台push_asset下载同样不取checksum；同平台推送current_exe是另一合法来源，不能强制当GitHub asset校验，应记录本机精确内容摘要再验证传输。onset release的checksum是积极对照，但latest bin与latest sha两次请求仍可能跨tag，主要表现为安全失败而非成功混装。

SHA256只能核对“选定来源所宣称的精确字节”，不能把同一路径下载的digest宣传成独立签名认证；plain HTTP镜像示例的真实性假设与HTTPS源不同。此次无新增签名/信任模型决定。

### Q041-D04 · P1/P2：默认onset源码构建可安装缺Pi运行组件的release

onset SOURCE默认build（:59附近），build分支:224–226只cargo zigbuild，不先构建GUI/Pi、不校验显式KHOR_AGENT_BUNDLE。node/build.rs只有设置该env才启用khor_embedded_agent，缺省仍允许desktop release成功。khor_agent.rs:482–507的非嵌入release只找可执行文件旁khor-agent；TypeScript源码fallback仅debug_assertions。onset只传khor本体，因此在env未设置、目标旁无既有sidecar时，安装/version检查可成功而首次Khor agent失败。已有dist还可能来自旧GUI源，web build只检查存在/可嵌入，不证明与HEAD匹配。

CI release/build-on显式编译嵌入，所以不是所有发布入口都坏；这是构建入口约束不一致。未实际安装或跑新release，分类为代码条件缺陷，修复前应补mock command/构建前置真实回归。通用开发Cargo无bundle是现有合法模式，不应全局禁止；应在生产构建入口强制完整组件来源与target，缺失时在任何远端写之前失败。

### 选择结果：tag只选一次，URL不再读取current

- `requested_version`仅为literal latest或安全tag；建议安全tag是单一Cargo SemVer tag：`vMAJOR.MINOR.PATCH`，可有合法prerelease/build metadata，总长<=128 ASCII bytes，无空白、换行、斜杠、百分号、反斜杠、query/fragment。VERSION文件<=256 bytes，仅一tag+可选单LF；不把任意trim后的输入当合法，也不允许VERSION本身写latest。
- mirror最新：只GET一次`<base>/VERSION`，取得tag后仅请求`<base>/releases/<tag>/<asset>.gz`和同目录同名`.gz.sha256`。后续VERSION变动/缓存旧值均不影响已选路径；旧代必须继续存在。显式tag完全不读取VERSION，只取该tag目录，缺失明确失败，绝不装current或退到平铺资产。
- GitHub latest：一次逻辑解析`https://github.com/<repo>/releases/latest`到同一可信repo的规范`/releases/tag/<safe-tag>`；解析结束即固定tag，再取明确`releases/download/<tag>/...`。redirect链中的多个HTTP请求属于这一次解析，不再独立解析第二个latest。KHOR_REPO本身须owner/name两安全段；域名/协议/凭据/query/fragment不从未验证header继承。实际asset的GitHub CDN跳转由HTTPS下载器处理，最后必须按选定tag/asset的摘要核字节；这与metadata canonical URL验证分层。
- 共享resolver返回逻辑结果`{tag, archive_url, checksum_url, expected_basename, source_kind}`，不能只返回一个可能再次经过latest的URL。正文与digest复用同一不可变selection。解析失败不调用place、不修改旧binary。

### curl与wget adapter的明确范围

- curl路径用最终effective URL确认规范tag，但HTTP非成功、歧义Location/多块header、重定向次数、长度限制仍须检查；只拿最后一个grep Location不能证明规范最终位置。建议接收最多20次redirect、64KiB总体响应header/诊断、8KiB单行；失败/超限不得继续。具体捕获必须保留下载器退出状态，不使用会吞生产者错误的管道。只有post-hoc wc检查不足以声称捕获内存/磁盘硬有界；若首批只实现接受长度上限，需明确该限制，硬capture helper另具独立fixture。

### 完整性与preplaced来源契约

- 当前release用shasum生成的是`<64 lowercase hex><两个空格><精确asset basename>.gz`加LF。首批固定接受这一单条格式（可无末尾LF），拒绝空文件、额外行/注释、多个digest、错误basename、`./name`、绝对/父路径、`*name`等其他模式；不让-c工具替我们选择另一个文件来验证。digest文件本身小限额，不能将任意网络正文直接交给sha工具。
- 下载摘要是**压缩归档字节**SHA256，先验证再解压到唯一目的目录stage，保留gzip/magic与最终same-FS rename。任一步失败保留原binary；先验证preplaced文件再消费/移动，失败不销毁调用者原文件。
- 建议新join使用`KHOR_ASSET_SHA256`传送本次preplaced归档的64hex精确摘要，和KHOR_ASSET_FILE成对必填；不能缺失就跳过校验。跨平台从选定tag下载后先核published sha，再将同一已核bytes+digest交远端；同平台current_exe→gzip后从**实际将传输的同一字节buffer**计算digest，不冒充GitHub release来源。SHA256只证明所选来源/本机与传输字节一致，不叫release签名。
- 85a78fe9已存在workspace sha2=0.10、khor-node sha2.workspace=true、锁0.10.9，无需新增Rust依赖或改锁。不要因为同锁另有sha2 0.11而升级这一链。
