## Findings

### High: queued cancellation can lose to newly consumed write approval (static, not run)

`crates/node/src/khor_agent.rs:731–735` newly calls `pending.poll` after **every** successfully processed Pi event. `McpSession::poll` at 965–995 consumes an accepted approval, clears it and calls `start` for the write. The only cancellation-notification observer is `message` at 887–902, reached when the execute loop later consumes that particular queued MCP event.

Concrete minimal sequence: a write is waiting in `pending`; the user's answer has set its exact active approval to Some(true); the bounded event channel already contains a legitimate update followed by `notifications/cancelled` for that same request. Processing the update now immediately polls and starts the approved write worker before consuming the already-queued cancellation. The worker can enter dispatch and perform a write before the next loop iteration retires it. Old code consumed approval only in recv_timeout's Timeout branch, after queued messages were drained. The retained comment at 659–660 explicitly promises processing queued cancellations before consuming an answer and starting a write.

The existing `cancelled_or_stopped_mcp_requests_cannot_consume_a_later_approval` test invokes message(cancel) directly before poll, so it does not cover this execute/channel ordering. This finding does **not** claim a runtime red or extend the original held-IPC red. Root/author were notified with exact source and sequence. Suggested minimal direction: keep fair polling of an already-running worker, while ensuring a bounded batch of already-queued cancellation events is processed before admission of an approved write; do not solve event-flood starvation by silently weakening cancellation priority. A deterministic queued update→cancel fixture should assert the tool never enters its side effect before treating this path as covered.

Author independently confirmed this exact ordering is possible and no current control prevents it. Proposed response is to separate worker completion/Stop polling from approval/heartbeat consumption and preserve approval polling only after queued events drain, pending root decision/new freeze. This agreement strengthens the source finding, but is not an executed business red; old 143713 evidence cannot prove a subsequently changed frame.

### Low: absent cancel requestId aliases explicit null (pre-existing for approval)

At 891/898, indexing `request["params"]["requestId"]` supplies JSON null when the field is absent. That equals an explicitly null-id active operation or pending approval, allowing a malformed cancellation notification without requestId to retire/clear it. Pending approval had the same comparison before this change; this is not the withdrawn missing-id ordinary notification finding. Consider requiring field presence before comparison. Valid SDK-generated cancellation IDs are the operative path, so this is a small input-shape hardening observation, not a separately established behavior failure.
