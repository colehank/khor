## 推荐最小方案：保留small-sync，增加协商后的有界blob追赶

首选完整delta或完整snapshot的**传输分片**，而非把任意原始CRDT bytes切开直接merge。既有Doc仅提供整段export，保持其边界可以先不扩展所有Doc adapter。单个大map值也可能超过页限；仅有“每页若干ops”不足以覆盖它。

1. **明确能力与新请求。** 增加只读sync-catchup能力请求/响应与专门新请求variant，尾追加，不给现有positional Sync/Synced字段加尾巴，不复用epoch或随意在base64里塞私有前缀。只在明确cap支持后使用新响应；按连接代次缓存能力，重连重探。旧端拒绝cap即走原small-sync。
2. **固定内容。** producer按同epoch、同doc、同base VV生成不可变完整delta；必要时用包含完整历史的snapshot。先完成本地flush，捕获与bytes对应的版本边界，将bytes落私有临时文件并绑定内容digest、总长、export种类、epoch、doc、对端身份和过期时间。后续本地写入产生后续增量，不改变已发布blob。不得用shallow/state-only或JSON重建悄悄丢历史/重铸writer IDs。
3. **有界传输。** 初选256KiB raw chunk（加base64/信封仍明显小于4/6MiB），pull/push均由明确transfer ID+offset调度；stage只存私有文件，offset/length检查防溢出，重复chunk需一致，所有文件名来自受控digest而非对方路径。分别约束并发、每peer/cache磁盘配额、TTL和整体blob上限；超过资源政策要明确返回需文件road/升级/管理处理，不能静默反复同一失败。这里降低的是每帧/内存/控制流占用，不是伪装“把4MiB换成更大常数”。当前Loro整段export/import仍需O(blob)空间，必须诚实给出总资源限额，不能声称无限大doc可无界导入。
4. **只在final推进文档。** chunk持久offset只是stage进度，绝不作为Doc VV或Peer.their的ACK。全部bytes到齐、digest/长度验证且epoch再次匹配后，才调用同一merge→took_in→flush→record-version路径；flush失败不得推进ACK。不要重复实现两份顺序。完整blob两次finalize要靠CRDT IDs幂等，不重铸新op；已经成功但ACK丢失可安全重送finalize。
5. **断线与重启。** source pinned bytes和接收stage/checkpoint采用私有落盘/原子元数据，ACK offset不得早于对应durable stage。重启按对端/doc/epoch/digest校验恢复；blob过期或epoch变更就丢弃stage并重新谈，文档VV仍未推进所以可重试。接收方已有本地写入必须merge保留，不能replace整个doc。
6. **公平调度。** 每doc每轮只给有界页预算，pending catchup驱动立即后续轮但先轮转Seen/Pins/其他doc，不在一个serial exchange里传完整大blob。mandatory doc pending/失败要明确记partial/failed，不能报整轮同步成功；同时不再因一个大doc立即放弃所有后续文档。继续保留answer的反向小delta merge/flush保护。

producer pinned snapshot/VV必须是一致切面，不能在export后随便采一个更晚的VV当作“接收方已拥有”；若源在传输中继续增长，完成旧blob后仍需正常version比较拉后续增量。

## root要求的只读补查：具体落点与资源边界

### 优先复用现有能力声明，不先发未知variant

找到比独立新cap请求更稳的既有机制：`link.rs:85–88` 的 `ROWS_BY_CHANGE="sessions+"` 放在现有 `Request::Versions.readings`。`versions_request:10485–10518` 声明它；`answer_versions:10658` 识别声明后才可能给新版SessionRowsSince。旧端`reading_request:151–165`对未知kind返回None，由filter_map跳过，不触发Request enum解码错误。

**修订推荐**：同形添加明确版本的标记如`sync-blob/1+`，保留现有Versions外形；新server在识别标记后，返回同marker的小型明确能力ACK（新client先抽出处理，再将真实reading交take_readings）。ACK必须在普通reading的1秒异步deadline之外同步生成，不能因quota读取慢而把能力漏报。标记不可匹配sat/、days@等真实reading前缀。

仅收到合法正ACK后才发新typed bulk请求。旧Versions端只跳过marker；更旧、不识别Versions的端沿既有fallback，并按连接缓存不支持，避免每轮试bulk。超时/格式错/认证拒绝不是能力支持，不能乐观启用。连接缓存键使用`line.conn.stable_id()`（wires.rs已有同类代次保护），不是只用line.id；新连接重探，旧连接迟到结果不能改变新连接能力。

默认**只piggyback现有opening的Versions**，不额外抢发cap-only RPC；这样对旧端没有新unknown variant或额外失败回合。只有已明确收到过该连接正常Versions、确认其支持外层请求之后，才可用docs为空、仅marker的cap-only刷新避免大doc加载拖慢能力判断。不能对会关闭未知请求的旧端每次redial都抢发新探针、重连后再试，从而制造永远进不到legacy sync的循环；完整Versions缺ACK才判不支持，网络超时保持unknown并依原road backoff。

这里只复用**能力声明通道**，不把bulk bytes塞入Versions.readings或reading cache。bulk数据仍走协商后的新请求，旧端永远不收到陌生bulk variant。当前未知Request→Refused处理是额外保险，不作为反复试错策略。

Versions已在`Request::rides_early`允许的只读集合；因此marker处理仅返回常量能力，不创建stage、不导出blob、不推进VV。首版bulk begin/chunk/finalize继续等完整认证握手，不因复用marker把写入/资源reservation塞进0-RTT。

### Doc层实际边界

以下是Doc公开本地写入与通用import边界，不等于所有上层CLI/GUI入口都没有各自限制；上层HTTP body/agent输出限额不能替代Doc总历史限制，也不能约束所有导入来源。

| Doc | 本地value形状与已见限制 | 可用于同步资源预算的硬上限 |
| --- | --- | --- |
| DeviceDoc | name、addrs JSON、style/road等字符串；upsert相同值不写，变化保留历史 | 未见单value/key字节、条数或历史总字节上限 |
| ChatDoc | tell原text、command/agent等记录；未知字段保留 | 未见text/记录bytes或历史总量上限；消息数显示不等于日志限制 |
| AccountDoc | Account序列化JSON为一个map value | 未见序列化bytes/条数/历史上限 |
| AgentDoc | Spec.launch及探测/会话配置等字符串 | 未见完整value bytes/历史上限 |
| TitleDoc | trim后的title | trim不限制长度；key/title bytes/历史无上限 |
| RecentDoc | timestamp i64、可选origin字符串 | timestamp类型固定；key/origin bytes和历史无上限 |
| SeenDoc | i64 watermark；只允许单调增加 | 数值固定；key bytes/更新次数/历史无上限 |
| PinDoc / DirPinDoc / WebPinDoc | bool value | value本身固定；key bytes/条数/翻转历史无上限 |

全部Doc的import最终走`glue::merge→LoroDoc::import(&[u8])`，没有统一bytes/ops预算；ChatDoc也转发同一glue。`wire::merge_b64`先base64 decode成Vec才判断4MiB，实际Node外层6MiB frame仍提供网络输入上界；直接Doc/file import没有这个wire门。

`glue::changes_since / snapshot`及锁定Loro1.16.2的`export`都返回完整Vec。`changes_since_b64`是在export完成后才检查4MiB，不能将现有门描述成“导出最多分配4MiB”。`store::flush`也会先导出完整本地delta；`table_b64`还会分配完整snapshot与base64。`store::read_once`用fs::read读整个块，再import；块大小不受MAX_BYTES约束。compact仍是包含完整历史的snapshot，不会自动消掉本缺口。

`store::KEPT`保留Arc<Vec> snapshot，未发现按字节或LRU预算的淘汰；只有reseed路径显式remove对应dir。`READING`每目录gate也无数量回收。cache命中仍D::open新Doc后import snapshot，缓存bytes和解析后的Doc会同时存在。它们是既有资源边界，chunk协议不能替它们提供全进程内存上限。

额外只复用现有尺寸probe（无重编/Cargo）执行`/usr/bin/time -l ./sizing`：该25,445,893B数据的生成/导出实际maximum RSS **168,476,672B（约160.7MiB）**，peak footprint 163,414,568B，运行1.12秒；日志`sizing-memory.log`。这尚未含BlockStore cache/网络stage；只是一个实测点，不能外推为固定放大率或整个App峰值保证。

### 固定export与VV不能ACK超前

本地Loro `ImportBlobMetadata.partial_end_vv`的注释明确说它不是完整VV，只含blob涉及的peer。不能把这个字段直接当整doc目标；也不能export旧bytes后读取一个更晚的doc.version作为接收方已拥有版本。

当前`with_doc!`取得owned Loaded；`load_cached/kept_copy`是D::open后import快照的独立Doc，不是把全局共享可变LoroDoc直接借给所有写者。应利用这个边界：在同一个owned Loaded上flush，捕获完整target VV，export，核对export后VV未变；必要时再flush并核对VV。导出含auto-commit或意外并发造成VV变化时，丢弃未发布blob并有限重试，不能换成更晚VV后照发旧bytes。其他Loaded并发落盘的新写入不属于本blob，下轮重新加载/版本比较追上。

descriptor固定doc/epoch/baseHave/完整target VV/digest/length/export mode。验证blob metadata只作一致性辅助，不能把partial VV冒充完整。最终merge后，接收方自己的Doc.version必须dominate advertised target（同时保留原本本地版本），否则不得发完成ACK；epoch在最终加载/flush前再核对。只有接收方真正merge并flush后返回自己的durable VV，chunk offset不进入Peer.their。并发新源写入即使出现，也不能被旧blob的ACK说成已接收。

另一个关键点：`decode_import_blob_meta`**不是**低内存header预检。vendored `fast_snapshot.rs:541/570`分别新建LoroDoc并复制oplog/body，再decode_change_store/decode_updates汇总VV；它也有O(blob)/oplog开销，不能重复全量解码后假称已做廉价内存门。首版可在producer做一致的owned export，在receiver检查digest/长度/epoch后单次merge并检查结果版本，不为了“预检”重复导入整段。若需低分配元数据验证，要先为Loro提供真正受预算的接口，不能假设现API有这个性质。

本地源码还确认`Doc.version→oplog_vv→OpLog::vv→dag.vv`，缺因果依赖的pending_changes尚未进入DAG；所以完成ACK要基于已整合的版本，不能基于payload内宣称的counter。`glue::merge`当前会忽略ImportStatus.pending，若后续改为op-range分页，必须另证pending恢复/持久化，不能把成功返回()当全部ops已应用。

这些是建议约束，尚未实现或用新协议并发故障注入验证。

### 旧端超限怎样不吞后续文档

现代路径已先take_readings，所以并非所有UI读数都停止；问题是mandatory doc失败会提前return，后面的doc没机会跑。optional doc本来就允许失败后继续；现代跨epoch错误也已允许跳过该doc，说明逐doc失败隔离有既有先例。

推荐在`sync_what_changed`和`sync_everything`统一收集mandatory失败，继续后续独立doc和读数；devices失败时不调用仅属于devices成功的follow_after_sync，其他doc仍按原认证/各自epoch合并。轮末返回聚合partial/failure，保留每doc原因；不能把部分推进改成全轮成功。为超cap/不支持bulk做按peer+doc+目标VV的诊断去重/backoff，而非每tick重算同一25MiB export；源VV/对端VV/能力或连接代次变化才重新评估，避免日志和CPU风暴。

去重不等于每次本地VV一变就重新全导出：devices会持续写，仍需每peer/doc的计算速率预算。建议不支持bulk且已证超限时，短暂backoff（例如30秒）只抑制大方向的重新export；请求方Have变化/能力或连接代次变化可提前复核，反向小输入仍要merge/flush。服务端legacy回答即使复用最近超限诊断，也不能连小输入一起跳过。具体策略须在实现里以新VV、旧端恢复与诊断不假报大小测试确定。

这里需补真实两Node transport验证，特别是Seen/Pins继续推进、mandatory失败仍可观察、旧端无新variant请求、epoch不跨越。当前研究driver只证明现有早退形态与后续Seen自身可同步。

### 可审查的首版预算与选择

建议首版明确“**传输/落盘有界**”，不要命名成“整个同步链路/进程内存已全有界”。以下是**拟议值，未实施**：

| 项 | 移动端 | 桌面 |
| --- | --- | --- |
| 每chunk raw | 256KiB | 256KiB |
| 单blob接受上限 | 32MiB | 64MiB |
| source pin + receiver stage总磁盘reservation | 128MiB | 256MiB |
| descriptor/版本metadata上限 | 64KiB | 64KiB |
| transfer ID数量 / 每peer | 全局16 / 每peer2 | 全局16 / 每peer2 |
| heavy export或final import并发 | 全进程共1个（两类共用门） | 全进程共1个 |
| in-flight chunk | 每transfer1个，受全局reservation和ID门约束 | 同左 |
| idle TTL / absolute TTL | 10分钟 / 24小时 | 同左 |

总长在创建stage前做reservation；不能16个transfer各自声称64MiB，最终把全局256MiB门挤爆。TTL仅清stage/pin，不清用户doc/ledger；活跃validated chunk刷新idle，绝对TTL不刷新。超过预算明确RequiresFileRoad/ResourceLimit，保留小反向更新和其他doc；不得静默跳过并报synced。32MiB覆盖本25.4MB复现，但**更大合法总缺口仍可能需要文件road或后续op-range分页，不能声称任意大历史已自动恢复**。

额外磁盘不是只有stage：final flush还会产生新的用户block，后续compaction可能写完整snapshot。建议接受时至少预留stage+新block+临时发布的保守空间（可先以3×blob加移动端256MiB/桌面512MiB余量作准入政策），统计与reservation必须覆盖source pin及receiver stage两类，临时文件atomic rename不能重复占预算。此估计仍需对实际export/flush膨胀测量，不是现API保证的精确上界。

相同transfer的finalize重试必须join同一个正在执行的job，不能一个超时就重开第二次import。TTL也不能释放仍在使用的stage/pin或heavy门；需明确Finalizing状态及结束清理。超时只能报告pending/late，不能声称已停止无法取消的Loro同步调用；硬截止属于下述B方案的前置工作。

hard guarantees仅为有明确检查/状态机支撑的chunk、排队、stage磁盘、已接受encoded blob bytes、并发数量。完整export在size检查前就可能分配超预算；final import还要read整blob并触发Loro解析/状态内存；KEPT与文档本体另占内存。所以这些值不提供32/64MiB RSS保证。spawn_blocking+timeout也不能杀死已开始的同步export/import，不可叫硬CPU截止。

具体选项（由root决定下一批，不空问用户）：

- **A，建议最小后续批次**：上述有限资源政策下的新新bulk恢复、marker协商、旧端错误隔离/明确降级。先关闭本25MiB业务红，测真实桌面/物理iPhone峰值，再按支持规模发布；明确尚无全CRDT内存硬保证。
- **B，若上线前必须硬保证所有内存/时间**：先增加Doc写入/导入/常驻cache政策，并为锁定Loro补预算/流式或可控因果分页能力；仅分chunk不够。helper进程也只能约束helper，父进程Doc/cache仍需限制，且iOS不能假定任意子进程方案可用。这是更大前置改造，不能藏在小协议patch里。
- **C，安全的临时/legacy路线**：先只做逐doc继续+去重诊断，明确超过现有门需文件road/升级；不改bulk协议。它能解除其他doc连带阻断，但不算B04自动恢复修复。

A与B都需在实施任务中规定单大value、版本metadata过大和历史总量超政策的可观察行为；不能因为本地setter今天没有上限，就暗示有限设备可透明接纳任意大合法CRDT。
