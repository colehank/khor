## 有界输入设计核对（待 root 确认后实施）

- read_text 响应/可编辑文本64MiB：apps/gui/core/src/files.rs::TEXT_CAP；write_whole 实际写限64MiB：crates/node/src/files.rs::WRITE_CAP。read_text 请求仅路径，不能限制响应；write_text 需要允许完整64MiB字符串及其 JSON 转义。
- merge_text 接收 base/mine/theirs 三份完整可编辑文本；合计可达192MiB，不可套1–8MiB统一 encoded cap。
- chat_say 的 msgpack MAX_PARTS=64MiB，包含 text、base64 images、files 等；JSON 的转义可能比其解码内容大6倍。
- upload/chat_put 使用 save_upload，实际1GiB；term_drop_stage 使用 drops::CAP=200MiB，term_drop_stage_into 为同一200MiB目录总量预算。四路保持既有逻辑/路径及界限；不能将“raw都1GiB”的摘要覆盖实际规则。
- 拟流式解析而非一次读取整 body String。普通 decoded 字符串合计64MiB+1MiB元数据，merge 192MiB+1MiB；单字符串64MiB，encoded按6倍+结构余量；每容器65536、总节点262144、深度沿serde128。流读取器先计 encoded、转义后的字符串 bytes/token，再交 serde 构造；visitor 在扩大 Value 容器前计宽度/总数。这样不会只在完整分配后才拒绝。
- 当前部分命令（post/seen_snapshot等）没有原始显式限额；上述预算会明确拒绝过去可无限增长的请求，是需要记录的新输入限制，不声称所有无限输入都兼容。20,000条目录路径与 DropItem 现有树限制需覆盖兼容测试。

## 下层阻断：tiny_http Request清理仍会按Content-Length分配

审查实际tiny_http0.12.0：util/equal_reader.rs::Drop 使用 `vec![0; remaining_to_read]`，remaining来自请求Content-Length剩余。JSON提前拒绝/读取失败后，Request析构会走这里；只改Web parser仍可能在下层一次分配攻击者声明的巨量内存，不能宣称整个请求生命周期有界。Request没有公开取换reader/关闭socket接口，不使用unsafe窥私有字段或mem::forget泄漏规避。

实际std-only探针直接include原registry EqualReader模块，以声明4MiB未读body+立即I/O失败的Read捕获它实际收到的buffer长度；精确1项真红、2 filtered，实际cleanup buffer为4,194,304字节。未制造大内存/OOM。证据 `Q032/tiny-http-cleanup-red.log`。已报root，请其决定vendor本地可重复补丁/公共依赖映射归属；本任务不擅改公共Cargo/registry。固定缓冲可以解决这处堆分配；耗时/慢请求deadline及是否终止剩余drain是独立传输约束，尚未声称解决。
