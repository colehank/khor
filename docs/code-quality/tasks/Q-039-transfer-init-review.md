## Design review and implementation conditions

The proposed one exact reserved `.initializing` namespace fits gate serialization: an acquired real gate proves no cooperating initializer remains, while active Sinks are only published final IDs. No chunk is admitted before publication. A complete synchronized-but-unpublished initializer can be discarded/retried because only its empty body and bounded controls exist; declared network body bytes are never valid there. This does not authorize cleaning damaged final64hex directories.

The safety conditions in the design should remain explicit in implementation:

1. Reconciliation occurs under the same LOCAL+OS Gate before reservation/owner checks, and create/initialize/publish/owner binding retain that gate. All public gate entrants must use the same reconciliation path; a no-gate helper should not become an accidental entry point.
2. Inspect the exact namespace and all at-most-three legal controls before deleting any sibling. Allow only regular private/root-owned unique-link manifest≤64KiB, body length0 and offsets≤72B; reject and preserve unknown names, excess entries, directories, links/reparse, owner/mode failures and oversize controls. A bounded listing must detect a fourth entry before any deletion. Cleanup interrupted between unlink operations remains another legal subset to reconcile.
3. Cleanup on ordinary initialization failure has authority only after successful mkdir of this namespace, preserving the existing failed-mkdir sentinel invariant. Retain original error plus cleanup error. Use exact unlinks and remove-empty-dir, not broad recursive/prefix GC. Never clean the final destination on publish conflict.
4. All three initialized controls must be written and synced, their handles closed, and completed binding checked before a single no-replace same-volume publication. Existing final target, including an empty directory or sentinel, must survive. Unsupported syscall/filesystem capability must fail closed, not fall back to std rename or check-then-overwrite. After publication, any later failure leaves a complete charged stage resumable through current API.
5. Check retained quotas and owner admission before unpublished creation; unpublished data is bounded control overhead, never a second transferable blob reservation. After publish the declared bytes/stage count are counted once. Keep no fallible operation after LOCAL owner insertion, to avoid recursive Owner Drop while the gate mutex is held.

Within the private exclusively managed root/cooperating-writer precondition, these conditions provide reviewable deletion authority without PID age guessing. They do not establish protection against arbitrary hostile same-user mutation of gate/path identities, Windows ACL enforcement, directory power-loss durability or a multi-file transaction. These boundaries are already honestly separated in the proposal.

## Platform source checks and remaining unknowns

Primary references were independently checked for the proposed helper choices, without compiling/running them:

- Apple [userspace XNU stdio header](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/stdio.h) declares renamex_np/renameatx_np and RENAME_EXCL=0x4 with availability annotations. Apple's [exclusive rename volume capability](https://developer.apple.com/documentation/foundation/urlresourcevalues/volumesupportsexclusiverenaming) makes filesystem support explicit. This supports the proposed direction but does not substitute for the eventual helper's exact errno/cfg behavior and conflict tests; unsupported volumes must not become overwrite fallback.
- Microsoft [FILE_STANDARD_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info) uses two LARGE_INTEGER fields, DWORD NumberOfLinks and two BOOLEAN fields. Native repr(C) with the proposed widths is appropriate; query/handle/reparse checks still need actual implementation review. Rust's [Windows MetadataExt](https://doc.rust-lang.org/stable/std/os/windows/fs/trait.MetadataExt.html) still labels number_of_links nightly-only, so stable metadata is not itself proof of link uniqueness.
- Microsoft [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) describes same-drive directory moves and separate replacement/copy flags. Avoiding replacement/copy is the intended direction; Windows runtime, sharing/close behavior and current helper FFI are not yet proven. Linux renameat2 selection/support remains to be checked at implementation time; this review does not endorse unimplemented flags/cfg or claim a Linux run.

The initial fixture covers one mkdir-before-manifest crash, not all future init phases. Required later implementation controls remain partial/synced manifest, created body, partial/synced checkpoint, before/after publication, interrupted cleanup, unknown/sentinel/link/private-owner refusal, final target preservation, owner/quota release, and original core controls. Node chunk/Pair/Applied receipts are outside this review; prior12/187 test results do not prove this new recovery design.
