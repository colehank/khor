## 下一可实现最小批：Q040a

建议先只改once锁表及其针对性测试；持久note/made/24h、三个调用点、wire、客户端creates map保持现有语义。

推荐保持`lock(&str) -> tokio::sync::OwnedMutexGuard<()>`不变：

1. 表值改成`Weak<tokio::sync::Mutex<()>>`。
2. 每次lookup在**同一个std表锁临界区**内先清除`strong_count()==0`的dead weak keys，再为当前token做Weak::upgrade；升级失败才创建Arc并存其downgrade。
3. 取得当前token的强Arc后释放std表锁，再`one.lock_owned().await`。std表锁不跨await，不等任何session/进程。

**为什么不会两把活锁并存：** 活guard、等待中的lock_owned future、刚lookup尚未await的请求都持强Arc。任意一个存在时，原Weak的strong_count非零且upgrade返回原锁；lookup/清扫/首次插入又被同一表锁串行化。只有这些强所有者全部消失才能创建新锁；此时旧请求已无能进入旧critical section的owner/waiter。清扫检测后刚好最后owner消失，只会多留一个dead weak到下一轮，不会误删活owner。不能先清扫后在表锁外upgrade/new/insert。

**回收承诺必须如实写明：** 这是下一次lookup时惰性清dead key；最后一个guard drop后不会自动启动后台清扫。顺序历史N请求不再保留N把锁，下一次lookup后只保留仍活/仍queued的锁及当前lookup条目；大并发峰值后若永久无新请求，dead weak keys和HashMap capacity可保留到下一次调用/进程退出。HashMap桶容量可能仍是峰值，不能称RSS立刻归零。若产品要求空闲时也立即回收，应另论带request lease的guard/取消Drop设计，而非偷偷加复杂析构或定时线程。

不接受的简化：

- unlock后直接remove：旧waiter仍持旧Arc，第三个请求可插入另一把锁，造成同token并行。
- LRU/TTL淘汰活项：请求慢、await或排队不代表token无owner；容量满应有明确admission政策，不能偷换锁。
- 只把Arc改Weak却不清dead key：String key与weak控制块仍按历史token累积。
- 一并删receipt或客户端intent：回执丢失会使安全重试成为新副作用。

最低行为测试（资源回收目标先红，排他/回执保持项基线先绿，再共同验证候选；作者本轮已覆盖下列1–5，6待串行集成按影响范围安排）：

1. 顺序N个unique token后触发清扫，证明idle历史不线性驻留，同时强活owner仍存。
2. A持同token、B已排队、A释放时C与清扫并发；互斥区最大同时数严格1，B/C不能拿两把活锁。用Notify/Barrier控制顺序，不靠sleep猜race。
3. 取消最后一个queued future、取消其中一个waiter、持owner时清扫、全部idle后同token再取得；旧owner不被提前回收、无死锁。
4. 不同token可并行，不把registry锁持到await。
5. 清掉锁后made仍返回原id；同token不会重做副作用，receipt内容/24h行为不变；错误路径资源也可回收。
6. 保留真实open_from_phone的相同startup只执行一次回归，按构建槽协调适当执行，不能只测map长度宣称端到端幂等全过。

本轮采用全局真实LOCKS+每测试唯一scope过滤，未增加生产debug API或额外LockTable类型。原2测试和新7测试已真实运行；后续由root独立复审并在精确集成版本验收。
