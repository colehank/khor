## 一、最重要的一件事：GUI 会话列表不渲染的根因已找到并修复

### 现象

Windows 桌面窗口能开、能画机器仪表盘，但**会话列表永远停在骨架屏**（4 个 `data-skeleton`），没有任何错误。

### 排除过程（每一条都是实测，不是推断）

| 假设 | 结论 | 证据 |
|---|---|---|
| 后端查询慢/失败 | ❌ 排除 | `list_sessions` 对 5 种排列全部 80–120ms 返回；`POST /api/sessions` → 200 |
| `RootPermit` 进程内自锁 | ❌ 排除 | 同进程第二个 `Node` 对同一 root 126ms 应答（`self_open_probe`） |
| tokio 阻塞池饱和 | ❌ 排除 | `off_main` 追踪：进入 14ms、完成 310ms、正常结算 |
| `announceFinished` 抛错压住渲染 | 已修 | 改为先 `setRows`/`setRowsRead` 再广播，广播异常单独捕获 |
| DevTools 读数可信 | ❌ 假象 | 隔离世界收不到 `invoke` 回调，DevTools 发起的 invoke 永远 pending |
| 窗口最小化导致节流 | 非根因 | 恢复窗口后 `document.hidden` 变 `false`，但 IPC 仍死 |
| WebView2 profile 损坏 | ❌ 排除 | 全新 profile 表现完全相同 |
| Tauri IPC 队列上限 | ❌ 不存在 | 通读 `tauri-2.11.5/src/ipc/`，无 pending map、无计数器 |

### 真正的根因

在 `invoke_handler` 第一行加逐条追踪后，**每次运行都只到达 9 条命令**，之后永远为空：

```
[ipc] #1 set_window_theme
[ipc] #2 lock_state
[ipc] #3 config
[ipc] #4 tabs_list
[ipc] #5 page_icons
[ipc] #6 tabs_list
[ipc] #7 face_here
[ipc] #8 devices
[ipc] #9 day_strips
（此后无论页面发多少次，都不再到达）
```

而页面同时发出了 **38 次** `fetchSessions`，Rust 一次没收到，两边都无报错。

**决定性实验**：从页面直接 `fetch('http://ipc.localhost/lock_state')`——不经过 `invoke`、不涉及命令、不涉及回调登记——**40 次全部超时失败**。

结论：缺陷在 **wry 的 `WebResourceRequested` deferral 处理**。每个匹配请求会取一个 deferral（`wry-0.55.1/src/webview2/mod.rs:992`），只有响应真正回到页面才 `Complete()`（`:1008`）。响应设置要走 `PostMessageW` 跳回主线程（`:1152-1177`），这条路一旦不执行，deferral 永久泄漏，Chromium 每源 6 条连接被占满，后续请求全部堵死在 socket 池——**表现为"发出去但连 socket 都拿不到"**，与观测完全一致。

社区同类证据：Tauri 维护者对[同类问题](https://github.com/tauri-apps/tauri/issues/15435#issuecomment-4534008966)的答复是 *"We don't have a good solution for that yet, for now the work around would be just avoid reloading the window"*；另有[项目记录](https://github.com/debpalash/VoiceStudio/commit/86f5213055e9326dabfe5cf950c004a5b81e6b1b)custom protocol 与 postMessage 回退同时失效、`invoke()` 永久挂起。**上游无修复版本可升。**

### 修复（已提交 `7cbfe9d9`）

页面本来就有三条传输通道（`apps/gui/src/api.ts` 的 `call()`）：

```ts
if (bridge) return post(`http://127.0.0.1:${bridge}/${cmd}`, {}, args);  // 本机 HTTP
if (inApp)  { invoke(...) }                                              // Tauri IPC
return post(`/api/${cmd}`, ...);                                         // web face
```

新增 `apps/gui/src-tauri/src/window_transport.rs`：在应用进程内起一个 loopback HTTP 服务（端口 **1432**），分派到与 dev bridge、web face **完全相同的** `khor_gui_core::api::answer`（190 条命令）。窗口改为加载 `index.html?bridge=1432`，于是 `call()` 走本机 HTTP，**彻底绕开已死的 custom protocol**。

事件、窗口控制、拖拽区域、原生菜单都是 Tauri 自己的 API，不受影响。

## 四、环境事实（避免重复踩坑）

- **构建**：`CARGO_TARGET_DIR=F:\Temp\khor-target`；GUI 前端必须在**无 `#` 的路径**下构建（Vite 7 拒绝含 `#` 的根），实际用 `F:\Temp\khor-gui`，改完 `apps/gui/src` 或 `src-tauri` 要同步过去。
- **前端构建**：本机**没有 npm**，只有 node + pnpm。直接跑
  `node_modules\.bin\tsc.cmd --noEmit` 和 `node_modules\.bin\vite.cmd build`。
  pnpm 装依赖需要 `--node-linker=hoisted --shamefully-hoist`（phantom deps）。
- **`cargo test -p khor-gui --lib` 在本机跑不了**：测试二进制加载失败
  `0xc0000139 STATUS_ENTRYPOINT_NOT_FOUND`（该 crate 是 cdylib，缺入口）。
  这与本次改动无关，改动前就是这样。集成测试（`--test xxx`）正常。
- **测试用 store**：`F:\Temp\khor-try\home-nohash`（无 `#`，已排除路径问题）。
- **调试**：`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9223`。
  ⚠️ **DevTools 发起的 `invoke` 永远 pending**（隔离世界收不到回调），
  **不要用 DevTools 判断 IPC 是否工作**，要在 Rust 侧打日志或看 DOM。
- **ConPTY**：`vendor/portable-pty` 已修 `PSEUDOCONSOLE_INHERIT_CURSOR` 丢输出的问题（提交 `6b3d9e49`），不要回退。
- **安全约束**：C 盘路径引用（`C:`、`$HOME`、`%USERPROFILE%`、`%LOCALAPPDATA%` 等）会被 `dsh-delete-guard` 拦下，破坏性命令必须用字面量路径、不能带变量或通配符。这不是障碍，是防线。
