# W8 · 工作区与会话：macOS 的行为设计，以及 Windows 要怎么适配

2026-11-18 · 状态：**分析稿，等业主裁决**（不含实现）

这份文件只回答一件事：**"会话"和"工作区"在 macOS 版里到底是什么关系**，以及
Windows 上要让用户看到"进入一个项目、跟智能体对话"，需要改什么。

---

## 0. 结论摘要

1. **macOS 的设计里，工作区不是一个"更大的会话"，也不是"会话的分组"**——它是
   人对"我在哪儿做事"的一次**声明**。会话是行为的**记录**。两者刻意互不推导。
2. 会话列表按**地点（原始 cwd）**分组，是"记录"的视图；工作区页右栏是"决策"的
   视图。**列表里出现的目录组，不等于工作区**——这正是 Windows 上"看不到想象中的
   对话界面"的结构性原因：这个机器上一个工作区都没立（`khor ws ls` 为空），所以
   只有一个按目录堆会话的记录视图。
3. Windows 上另有一个**会静默失效**的隐患：工作区右栏用"路径前缀 + 分隔符"判定
   成员，而 Windows 上同一条路径的写法不唯一（`\\?\C:\…`、`F:\` 与 `f:\`、`/` 与
   `\`）。一旦声明时和记录时写法不同，右栏会一行都不显示，且没有任何报错——正好
   是 `WORKSPACE.md` 自己警告过的那个老毛病："答不了的分支不留白，变成它的邻居"。
4. 会话页那屏 `cmd.exe` **不是设计行为，也不是你建的**：是本轮自动化测试的产物
   （152 行里 140 行同名 `cmd.exe`）。本轮已清理，剩 4 行（含你的 `onlinenpx`）。
5. 本机**并没有安装 Khor**：只有便携 exe 运行留下的 `%LOCALAPPDATA%\Khor`
   （logs/runtime）与 `%USERPROFILE%\.khor`（数据），没有程序目录、卸载项、
   开始菜单快捷方式，`khor` 也不在 PATH。

## 1. macOS 的行为设计（事实，带出处）

### 1.1 一切交互都是会话

> "一切交互都是 session：shell、智能体 TUI、对话（对端是设备或智能体）、文件传输，
> 以及未来任何形式。像微信的会话列表——机制各异，同一张脸。" — `docs/SESSION.md`

每个会话只回答五问：**你是谁**（id/kind/title）、**你在哪**（home）、**你怎么样**
（六词状态）、**发生了什么**（events）、**看过没有**（unread）。列表层永远只有这
五问，新 kind 不改协议。

六词状态里 **"待批"排最顶**（只有人的准许能解），"等你看/等你说下一句"不算——否则
角标常年不为零，等于没有角标。

### 1.2 工作区是「人立的」，不是推导出来的

> "一个工作区 = **一台机器上的一个目录**，由人指定。" — `docs/WORKSPACE.md`

这是被明确裁决过的：khor 原先推的是"读各 agent 的会话记录，把 cwd 沿 `.git` 往上折
到仓库根，是仓库的就当工作区"，2026-09-14 业主否掉了这条路，两句话：

> 用户有 agent 记录的目录不一定是工作区，可能只是随手打开的。
> git 目录也不一定是工作区，很多工作区开始的时候不是 git 目录，或用户根本没想着用 git 管理。

于是**派生那条路整段删了**（`Node::workspaces_shown`、`Request::Workspaces`、
`Place.checkout`），只留下 `crates/node/src/place.rs` 喂命令行的 `khor places`。

工作区身份 = **`(device_id, 绝对路径)`**；名字 = 目录 basename；两台机器上都有
`~/w/khor` 就是两个工作区。

### 1.3 工作区页右栏 = 该机器、该目录**子树**里的会话

两条硬条件（`docs/WORKSPACE.md`「里面的会话」，实现见
`apps/gui/src/lib/session-cwd.ts` 的 `sessionInWorkspace`）：

1. `会话.home 频道名 === 工作区机器的频道名`（按 id 解析频道名再比，不比显示名）；
2. `cwd === 目录 || cwd 以 目录 + 分隔符 开头`。

第二条的分隔符是硬的：`/home/peer/workshop` 是 `/home/peer/work` 的邻居，不是孩子。
第一条也是硬的：两台机器都可能有同名目录。

**关键点：这个判定用会话的原始 cwd，不用折到 git 根的路径。** 2026-09-15 起
`SessionRow.place` 存原始 cwd（`khor_node::live::place_of`），原因写在文档里：

> 工作区立在 `~/w/paper/data`，而在那儿开的会话折完报的是 `~/w/paper`，对不上；
> 反过来工作区立在仓库根上，子目录里的会话全归它——看着对，其实是巧合。
> **原始路径随时能折，折过的路径回不去。**

代价也写在明处：会话列表按「地点」分组，一个仓库的两层是两个标题。

### 1.4 两个视图的分工

| 视图 | 它回答 | 数据来源 |
|---|---|---|
| 会话列表（按地点分组） | "我最近在哪些地方跑过东西" | 会话记录的原始 cwd |
| 工作区页右栏 | "我在这台机器这个目录下做的事" | 人声明的工作区 + 会话 cwd 前缀匹配 |

**它们不互相推导**：目录组不会自动变成工作区；工作区也不会凭空把会话"收编"。
中间的桥只有一座——**人来按"立为工作区"**。

### 1.5 入口（macOS）

- 工作区：列表头 `+` → sheet（`components/DirPicker.tsx`）挑机器 + **一个空路径框**
  （`components/PathField.tsx`），边写边补全子目录，**不推荐任何路径**（2026-09-27
  业主裁决）。sheet 自己不验证，`ws_add` 拿 `Ls` 去问那台机器。
- 新建会话向导的「目录」是同一个框（同一组件）。
- 命令行等价：`khor ws add|rm|pin|unpin|ls`。

## 2. Windows 现在的实际情况（实测）

### 2.1 没有安装

| 检查 | 结果 |
|---|---|
| `%LOCALAPPDATA%\Khor` | 只有 `logs`、`runtime`（运行时镜像/日志） |
| `%LOCALAPPDATA%\Programs\Khor`、`%ProgramFiles%\Khor` | 不存在 |
| 卸载项（HKCU Uninstall） | 无 |
| 开始菜单 / 桌面快捷方式 | 无 |
| `khor` 是否在 PATH | 否 |

也就是说：**Khor 在这台机器上是"便携 exe 跑起来过"，不是"部署了"**。数据存在
`%USERPROFILE%\.khor`（accounts/agents/cache/devices/day.json…）。

### 2.2 会话页那一屏 `cmd.exe`

清理前 **152 行会话，其中 140 行标题是同名的 `cmd.exe`**（全是本轮自动化探针反复
开会话留下的）；另有 2 行 `observe/` 测试导入。**不是设计默认，也不是用户建的。**

已用 `khor close <id>` 清理（标题为 `cmd.exe` 的 140 行 + 我的 9 个具名探针），
清理后剩 4 行：

```
shell/f57644bc8d970253   Idle    gui cross
shell/80ecd148329b0502   Idle    gongzhengxin
shell/e4a3b5cc34932aca   Failed  onlinenpx          ← 你的
observe/eaa934a2…        Read-only session  onlinenpx  ← 你的导入
```

### 2.3 工作区表是空的

`khor ws ls` **没有任何输出**——这台机器上从未立过工作区。所以界面上不存在"项目
视图"，只有按目录分组的记录视图。用户看到的"会话板块"= 记录视图，里面自然全是会话
记录，而不是"进入项目后的对话"。

### 2.4 同一条路径，多种写法（会静默失效）

实测到的两种真实写法：

| 来源 | 写法 |
|---|---|
| 会话记录的 `place` | `F:\#Gong\#AI4S\onlinenpx`（反斜杠、大写盘符） |
| 新建会话向导的目录框 | `\\?\C:\Users\admin\`（扩展长度前缀） |

`sessionInWorkspace` 只用 `root` 的形状猜分隔符（`/^(?:[A-Za-z]:\\|\\\\)/` 判 `\`），
然后 `cwd.startsWith(root + "\\")`。它**没有**处理：

- `\\?\` 前缀有无的差异；
- 盘符/目录名大小写（Windows 不区分，字符串比较区分）；
- `/` 与 `\` 混用（OSC 7 或第三方工具可能给正斜杠）；
- 尾分隔符、`.`/`..`、UNC（`\\server\share`）与盘符根的边界。

后果不是报错，而是**右栏空着**——和"确实没有会话"长得一模一样。

### 2.5 会话标题同质化

Windows 上 shell 会话的标题就是进程名 `cmd.exe`。140 个同名行，既无法区分，也强化
了"这是 CLI 坟场"的观感（macOS 上同类情形也有，但 Windows 的默认 shell 让它在列表
里更刺眼）。

## 3. 差距分析：为什么"看不到想象的对话界面"

分三层，按重要性排：

**A. 结构（最主要）**：Windows 上从来没有工作区 → 没有"项目视图" → 用户只能在
记录视图里翻会话。用户心智是"打开一个文件夹 = 进入一个项目，然后跟 agent 对话"，
而 khor 要求先显式立工作区（且入口在列表头的 `+`，与"打开文件夹"这个动作不在一处）。

**B. 形态（已修一半）**：新建会话的默认形态上一轮已改成 `Codex · 对话`
（`8899f1db`），但**存量** shell 会话让页面看起来仍是 CLI 坟场——已清理，且需要
"只看对话"这类默认过滤来防止再次堆积。

**C. 路径（潜伏 bug）**：工作区成员判定在 Windows 上会因写法差异静默失效；
一旦用户真的立了工作区却看不到会话，体验会比"没有工作区"更糟。

## 4. 适配方案（分三档，建议按序）

### A 档：先修不涉及产品判断的部分

1. **路径身份归一化**（`apps/gui/src/lib/session-cwd.ts` + 一个纯函数模块）：
   `pathKey(p)` 去掉 `\\?\`/`\\?\UNC\` 前缀、统一 `/`→`\`、折叠大小写（Windows）、
   去尾分隔符；`sessionInWorkspace` 两侧都过 `pathKey` 再比前缀。补单测：
   `\\?\C:\a` vs `C:\a\b`、`C:/a` vs `C:\a`、`c:\A` vs `C:\a`、UNC、盘符根。
2. **会话标题**：shell 会话在 Windows 上用「目录名 · cmd」而不是裸 `cmd.exe`，
   让列表可区分（与 macOS 的"同一张脸"不冲突）。
3. **清理已完成**，并给测试脚本加约束：探针会话用固定前缀标题（如 `probe-…`），
   跑完自清，避免再污染真实 store。

### B 档：把"立工作区"放到用户已经在的地方（需要你确认措辞与位置）

1. **会话列表的目录组头**加「立为工作区」——一次点击，明确是人的决定（不违反
   "人立"原则），做完跳到工作区页。
2. **新建会话成功后**，若该目录不是工作区，给一条可忽略的提示：「把 `onlinenpx`
   立为工作区？」。
3. **工作区页空态**不要空白：写清"工作区是你指定的目录"，并给一个「选目录」按钮
   （复用现有 `DirPicker`），而不是让用户去猜 `khor ws add`。
4. 新建会话向导默认带出**当前工作区**的目录（如果是从工作区页进来的）。

### C 档：需要你裁决的偏离

以下是相对 macOS 设计的产品性改变，我不擅自做：

1. **要不要允许"打开文件夹即建工作区"？** macOS 明确拒绝推导（2026-09-14 裁决）。
   Windows 用户更习惯"打开文件夹=项目"。折中：首次打开某目录**提议**、但仍由人确认。
2. **会话列表默认按什么分组？** 现在按地点；Windows 上是否默认按工作区优先、其余
   归"其他地点"？
3. **要不要"只看对话"过滤/默认隐藏终端会话？** 这会让列表更接近"对话界面"的
   预期，但会藏起真实存在的终端会话。

## 6. 业主答复与设计修订（2026-11-18 下午）

业主回了三条，其中两条改变了设计，一条纠正了我的表述。

### 6.1 「工作区可不可以关联多个文件夹？」 → 可以，且应该

业主的模型：**事业 → 多个项目 → 每个项目一个文件夹**，以事业为中心组织。

现状是硬约束：`WorkspaceInfo { device, machine, path, name = basename, pinned }`
（`crates/node/src/workspace.rs`），身份 = 单个 `(机器, 目录)`，名字由目录名派生、
**不存库**。一个事业横跨多个项目文件夹，在这个模型里必然拆成多行"工作区"。

提议（推荐）**工作区升级为"有名字的文件夹集合"**：

```
Workspace {
  id:     稳定标识（新生成，不再是路径）
  name:   事业名，人写的（集合没有 basename，必须存）
  folders: [{ device, path }, …]      // 一个项目一个文件夹；可跨机器
  pinned: bool
}
```

- **右栏**：任一个成员文件夹子树里的会话都属于这个事业（沿用现有的"前缀 + 分隔符 +
  同机器"规则，对每个成员各判一次，取并集；跨机器时按机器分组）。
- **名字必须存**：这是唯一一处与"名字永不存库"原则的偏离，理由是原则本身——
  "名字会漂移"针对的是**目录**的名字；事业是人造的名字，它本来就是人写的。
- **迁移**：现有每个单目录工作区读出来 = 一个只有一个成员的集合，名字沿用 basename。
  复制文档里加版本号，旧 khor 读到新文档按"未知字段"忽略（`SESSION.md` 开放性）。
- **创建**：`+` → 写事业名 → 加第一个文件夹（同一个 `PathField`）→ 「再加一个文件夹」。
- **命令行**：`khor ws add --name <事业> <目录>`，`khor ws folder add|rm <事业> <目录>`；
  `ws ls` 打印 `事业 → 成员`。

备选（较轻，不推荐）：工作区仍 = 单目录，另加"分组"层。它把概念变成两个（工作区 +
组），而业主要的正是"工作区本身能装多个项目"。

**分期**：① 文档与 schema + 右栏并集（可在旧数据上跑）② 工作区页头部 = 事业名 +
项目列表 + 加文件夹 ③ CLI 对齐。等你点头后从 ① 开始。

### 6.2 「会话板块本来就不是对话界面，这我没看懂」 → 我的表述错了，纠正

**会话区就是交互入口**，现在也是：

- 点一行 → 打开那个会话的面：终端会话是终端，对话会话是对话（`DetailPane`）；
- 列表头的「+」→ 新建会话向导 → 选 `Codex · 对话` → 创建后直接落在对话面；
- 在工作区页 → 右栏「+」在该项目的目录里新建，目录默认带出。

上一轮我写「会话列表是记录视图」，指的是**分组键**（按原始 cwd 分地点），不是"只读
日志"。这句话让你以为会话区不能派发任务，是我的错，已在本文修订。

那 Windows 上真正缺的是三件事，不是"会话区不是交互界面"：

1. **默认干净**：只看对话（已按你的裁决实现，见 §6.3）；
2. **空态引导**：列表空时给「派发第一件任务」按钮（现在只是"没有会话"文案）；
3. **从事业进入**：有了 §6.1 的集合，工作区页就是一个事业的项目列表，右栏直接
   「新建对话」，这才是"以事业为中心派发任务"。

### 6.3 「同意只看对话过滤，windows 上这么设定」 → 已实现

- 会话列表新增第五个筛选轴 **`talk:`**（标题「形态」，值「对话 / 终端」）。它是
  **行的面**，不是节点分组键——`AXES` 仍是节点那四个，`talk:` 只在会话页出现。
- **只隐藏三种**：`shell`、`transfer`、`borrow`。`tui`（智能体 CLI）与 `observe`
  （只读的 agent 记录）都算对话——它们是 agent 的真实工作；**未知 kind 一律保留**，
  否则新版本节点的新会话会在唯一能显示它的列表里消失。
- Windows 默认勾「对话」；其他平台保持原样（空筛）。用户只要动过一次筛选，就以
  存储值为准（"没存过"和"存了空"是两件事，已分开处理）。
- 词条：`axis-talk`（zh「形态」/ en「Form」），值复用 `view-chat` / `view-terminal`,
  避免同一段两个名字。
- 检查：`apps/gui/scripts/check-session-talk.mjs`，已加入 `npm run test:unit`。
