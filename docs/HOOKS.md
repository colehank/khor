# 接入:进程怎么把状态词交给 khor

session 状态不同步、home 现拿(NET.md);这页讲 home 上的进程怎么交词。
两条纪律:

- **智能体状态靠钩子,不靠抓屏。** 字符串匹配只留给非智能体程序兜底。
- **进程只许报活词**(忙碌/待批/完成/中断/空闲)。**失败由退出码推**,
  谁也不许自称失败——一个还能说话的进程说自己失败,必是谎话。

交词有两条路,**默认那条不需要用户做任何事**:

| | 谁动手 | 什么时候有 | 词准到哪一档 |
|---|---|---|---|
| **读盘发现**(默认) | khor 自己读厂商的文件 | 装上就有,连 khor 装之前起的会话也在 | 各家能给多少给多少,给不准的不给 |
| **钩子** | 用户装一次配置 | 装了才有 | 更准,补上读盘给不出的那几档 |

两条路指向同一行:id 都由 `adaptor::id_for` 铸,**同一个会话既被钩子登记
又被读盘发现时并成一行**。登记的那份赢——它有词的历史——**只有结局那一档
归读盘**:钩子登记的会话没有 pid,它的词只是「没人有资格宣布它死了」才立着,
而厂商的文件认得 pid。不这么分,装了钩子的用户查崩溃反而比谁都差。

## 读盘:零安装那条

实现在 `crates/node/src/adaptor/`,一家一个模块,**判据写在模块头里,
改之前先读**——那里有「为什么接缝现在抽、为什么只有一个方法」,以及
每家的落盘格式、活性判据、词映射各自的实测数字。这页只记别处没有的:

- **一行必须有活进程撑着,历史文件永远不是行。** 厂商的文件说「它是什么」,
  进程表说「它还是不是」。唯一的例外是崩溃:文件活过了它自己的进程,
  而厂商干净退出会删掉它,所以那是一个没人记的结局(失败),且只在
  24 小时内算数——几天前的崩溃也是历史。
- **认不出的不落词。** 不认识的状态值、读不懂的文件、连不上转写的活进程,
  一律不产生行,改为计数,`khor sessions` 末尾外显。
  **零行 + 零计数是机器闲着,零行 + 非零计数是 khor 过时了**,
  只有这个数分得开两者。
- **发现的行 khor 关不了**(它不是 khor 起的),`close` 会照实说。

发现器的根目录跟着 khor 自己的 home 走(同一台机器的同一个家),
`KHOR_VENDOR_HOME` 覆盖它——那是「khor 装在别处、但要读真的智能体文件」
的那条路,验收就是这么跑的。

**各家能给的词不一样,这正是不抽一张公共词表的原因**(细节和实测数字在
各自模块头):claude 的状态文件给得出待批,**给不出完成**(它的 idle 分不出
「这轮刚完」和「一直没动过」,所以完成显示成空闲——钩子装上才有);
codex 的转写给得出完成,**给不出待批**(它落盘里根本没有审批事件)。

## 门:`khor state`

`khor run` 给孩子设 `KHOR_SESSION`;孩子或它的钩子跑 `khor state <词>`
就写进那个 session。没有这个环境变量就 `--session <号>`。

## Claude Code 的钩子

各厂商的 hook 与命令各异且更新快,所以映射按 adaptor 养:门(上面两条纪律)
不随厂商变,每家一份事件→词的映射,数据优先、隔离存放。接缝已经抽了
(`crates/node/src/adaptor/`,codex 接入时按账本的触发条件动的手),
这份 Claude 的钩子就住在 `adaptor/claude.rs` 里,和它的读盘实现同一个模块。
认不出的事件不落词——时间戳自然老去,界面灰显,不许静默显示成邻居那档。

装钩子是可选的:不装也看得见会话(读盘),装了词更准——对读盘发现的会话,
**`Stop` 事件是「完成」的唯一来源**,不装的话一轮跑完只会显示成空闲。
(2026-08-17 放宽:`khor open --gui` 的 ACP 会话是第二个第一手见证——
khor 自己就是回合结束的那一端,不经钩子也报得出完成;见 `gui_host`。)

### 装法:`khor hooks install`

```
khor hooks           # 装没装、装的是哪个 khor
khor hooks install   # 装上
```

**不用手抄 json**(以前要,这段是改口)。判据都在
`crates/node/src/adaptor/claude.rs` 的安装那一节,这页只记别处没有的:

- **合并,不是覆盖。** settings.json 是用户自己的文件,里头通常已经有别人的
  钩子(这台机器上就有 mandala 的,盖着八个事件)。install 只往
  `hooks.<事件>` 里追加自己那一组,别的键、别的事件、同一事件下别人的组
  一律不碰——连**键的顺序**都不动(`serde_json` 因此开着 `preserve_order`)。
- **装两遍 = 装一遍**,而且它**说得出来**:第二遍打印「本来就有,没动」。
  一个人没法自己去核对文件,所以幂等必须是屏幕上看得见的话。
- **写的是这个 khor 的绝对路径**,不是 `khor`。钩子是 claude 起的,而
  claude 可能是从 GUI 起来的、PATH 里没有用户 shell 的那些目录。代价是
  khor 换了地方之后那条路径就指空了——所以 `khor hooks` 会**分开说**
  「装好了」和「装的是另一个 khor」,而不是把两者都念成「装了」。
- **读不懂的 settings.json 一律拒绝,绝不修**。那是用户唯一的一份,khor
  对它内容的猜测不是修复。
- **装在哪跟着 khor 自己的 home 走**(`adaptor::vendor_home`,和读盘发现
  同一个函数)。读和写必须同一个答案,否则 `khor hooks install` 配的是一个
  claude、列表看的是另一个——**而两边都不会报错**。
  `KHOR_HOME` / `KHOR_VENDOR_HOME` 因此也是它的验收姿势:全套验证跑在隔离
  目录上,一次都没碰过真的 `~/.claude`。

装完的样子(每个事件都指同一条命令,词由 khor 从载荷里判;映射收在
`khor state --hook` 的实现里,这页不抄第二遍):

```json
{
  "hooks": {
    "SessionStart":     [{"hooks": [{"type": "command", "command": "'/path/to/khor' state --hook"}]}],
    "UserPromptSubmit": [{"hooks": [{"type": "command", "command": "'/path/to/khor' state --hook"}]}],
    "Notification":     [{"hooks": [{"type": "command", "command": "'/path/to/khor' state --hook"}]}],
    "Stop":             [{"hooks": [{"type": "command", "command": "'/path/to/khor' state --hook"}]}],
    "SessionEnd":       [{"hooks": [{"type": "command", "command": "'/path/to/khor' state --hook"}]}]
  }
}
```

一条判进映射时定过的界:**Notification 只有要许可的那种才是待批**。
「等你说下一句」永不进待批——那个角标归不了零,等于没有角标(SESSION.md)。

三种跑法:

- `khor open --tui -- claude`:持久——终端关了它还在,`khor attach` 接回来,
  哪台设备都看得到词。宿主设 `KHOR_SESSION`,钩子的词落进同一个 session。
- `khor run --tui -- claude`:临时——一个 session、可靠 pid、真退出码,
  跟着这个终端活。
- 直接在自己终端里跑:什么都不用做也看得见(读盘发现)。装了钩子的话,
  钩子自注册的是同一个 id(`tui/<claude 的 session id>`),两边并成一行。
  **登记的那份没有 pid**(钩子的父进程是个临时 shell,不是 claude),
  所以它的词只是「没人有资格宣布它死了」才立着;而读盘那份认得 pid
  ——状态文件的文件名就是它。**结局这一档因此归读盘**:被硬杀的 claude
  会转成失败,装不装钩子都一样。
  **「观察 session 的 pid 探测」这条挂账对 claude 结清了**(靠它的状态
  文件),没有状态文件的厂商仍然挂着。
