## 3. 目标、边界与完成定义

目标：在用户允许且当前可达的路径中尽快完成操作，减少长尾卡顿，在网络变化后快速恢复，并控制后台耗电与流量。

设计约束：

1. 直连、中继、SSH 承载、设备转发均可凭实测表现胜出。成本只在体验接近时作为次级考虑；尊重用户显式配置，例如只使用自己的中继、暂停设备与信任名单。
2. 延迟、吞吐、稳定性按工作负载评价。较低 RTT 不自动证明传文件更快，较高吞吐也不自动证明终端更跟手。
3. 保留设备身份、端到端加密与个人信任模型。写请求不能因重连被悄悄重复执行；0-RTT 的请求准入边界不能因提速放宽。
4. 每层只有明确的职责和状态所有者，避免选路、连接退役、应用重试互相触发。
5. 先验证实际瓶颈，再增加复杂度。个人网暂时保留现有设备间连接结构，规模测试覆盖它的实际使用范围。

完成需要同时交付：设计说明与决策理由、状态/职责边界、可持续运行的验收矩阵、相同条件下的前后对照报告。仅编译成功、单次实验绿、增加中继数量或改掉 `direct_first` 测试，都不足以宣告整体完成。

## 6. 设计工作包与顺序

### N0：基线、证据与实验入口

- 核对当前源码、现有调用链、补丁和测试覆盖，补齐指标定义。
- 基线版本、候选版本、固定好路径对照使用相同网络配置和工作负载。
- 验证 Linux 执行器条件，建立 `khor-build` 的 netlab 调度和收据。规划时尚无该任务；现在分支入口已建立，具体任务与control版本见ACCEPTANCE/STATE，恢复时核对实际状态，不重复搭建已验证入口。
- 分类现有场景：稳定回归、已知未达标、执行器故障、尚未覆盖。
- 完成标准：基线可重复运行，源码可追溯，验收矩阵和门槛已经冻结。

### N1：按体验选路

- 明确路径事实：类型、完整端到端测量、近期停顿、波动、样本时间、有效性与可信程度。带宽信息只在有观测时使用，未知不当作零或无限。
- 移除直连硬优先，比较实际可用路径。将路径可达性判断与路径质量排序分开。
- 为明显收益设置有依据的确认条件；收益接近时保持当前路径；故障切换有独立的快速通道。
- 防止稀疏保活、积压 ACK、网络变化前的旧样本和 CPU 忙时的调度延迟污染判断。
- 明确同一对端多个协议/连接共享哪些事实，避免闲连接的旧状态压过活连接的有效测量。
- 完成标准：慢直连/快中继和反向场景均正确，稳定路径不反复抖动，好路径恢复后不会长期困在慢路。

### N2：首次连接、换路与恢复

- 近期成功记录参与尝试顺序，但缓存有失效规则；失败地址不能耗尽全部请求预算。
- 有界并发尝试候选，明确取消输掉的尝试、资源释放和用户取消的传播。
- 先获得可用连接，再在存续期间改善路径；保留少量有价值的备用，按使用状态调节探测。
- 请求期限向下传递，区分路坏、连接坏、远端处理慢和本机调度慢。
- 后台重试加入适当随机扰动、并发预算和恢复事件合并；前台动作优先但仍有预算。
- 保持读写重试和 0-RTT 安全边界；验证重连不会重复执行命令或写操作。
- 完成标准：换网、休眠、中继重启、黑洞均满足分场景恢复目标；没有泄漏、重试风暴或写入重放。

### N3：交互与批量共存、后台开销

- 检查应用队列、并发额度、发送缓冲、外层承载流中真正的阻塞点。
- 为交互/控制、前台内容、后台批量设计优先级、背压和公平推进。
- 比较共享连接调度与分连接方案；仅在实验支持时采用增加连接的设计。
- 保留个人网的现有拓扑，改进事件触发、闲时节奏和恢复时请求合并。
- 完成标准：大文件或同步不会制造不可接受的回显长尾，批量不会饥饿，闲置成本符合预算。

### N4：中继与寻址可靠性

- 测量设备 A→中继→设备 B 的完整路径，覆盖两端不对称可达性；不只按本机到中继的延迟排名。
- 模拟北京整机、香港整机、单一出口和地址登记服务故障，找没有替代路径的故障域。
- 评估单家约束和第二登记点/双家的必要性、实现可行性、资源成本；不预先认定必须再开一个 endpoint。
- 检查地址缓存失效、设备重启后地址变化、发布与发现是否能引导客户端使用新路。U12要求覆盖IPv4/NAT映射与IPv6隐私地址/前缀独立变化、同时变化、网络/地址族切换；包括peer relay自身移动。旧地址可作有界提示，旧epoch探测/关闭不得撤回新路；具体矩阵与记录见ACCEPTANCE。
- 按数据提出中继地域、供应商/线路、数量、容量和运维方案。部署与采购是独立执行事项。
- 完成标准：有测量支持的拓扑与故障切换设计；节点不可用时客户端实际能到达替代路径，容量限制不会隐藏成随机卡顿。

### N5：整体验收与补丁收口

- 对所有有行为影响的 vendor 补丁记录原因、覆盖场景、上游状态及保留/退出条件。
- 短场景进入网络改动回归，完整矩阵按需执行，长时间场景验证稳定性；不把已知红项隐藏成通过。
- 原生 Mac 验证与实际手机/多机网络验收独立留证；实验室通过不替代真机结论。
- 对最终集成源码执行适当完整检查。每次合并其他分支后重新核对相关证据的适用性。
- 完成标准：所有必需交付项有对应版本证据；剩余限制有明确说明；设计、代码和运维文档一致。

顺序：N0 → N1 → N2 → N3 → N4 → N5。N0 就开始收集中继测量；发现阻断体验的中继/寻址问题时可以调整顺序，但在 STATE 记录理由与依赖，不无声扩展范围。

## 7. 最小场景矩阵

| ID | 场景 | 核心验收行为 |
| --- | --- | --- |
| NET-01 | 慢直连、快中继，以及快直连、慢中继 | 路径类型不能压过明显体验收益 |
| NET-02 | 同速双路、小幅噪声、短时尖峰 | 稳定保持，避免无收益切换 |
| NET-03 | 当前路黑洞，另一路已可用 | 快速恢复且不丢失应用操作语义 |
| NET-04 | 长卡顿后好路径恢复、闲连接旧测量 | 不被过时 RTT/PTO 状态长期困住 |
| NET-05 | Wi-Fi 切换、地址/端口变化、睡眠恢复、后台回前台 | 新旧地址与缓存正确更新，恢复有总预算 |
| NET-06 | 中继重启、整机失效、只断一端、TCP 可建但不转数据 | 发现真实数据面故障，实际找到替代路 |
| NET-07 | NAT 组合、UDP 不通、IPv4/IPv6 单双栈、NAT64 | 可直连就实测参与比较，否则可靠走可用承载 |
| NET-08 | 代理、内部 DNS、受限出口、完全断网/门户 | 清楚区分不可达原因；无路时停止无效忙转 |
| NET-09 | SSH 与设备转发，中间设备冻结/恢复 | 覆盖内外层按序阻塞及恢复相互作用 |
| NET-10 | 传大文件并持续打字/取消/打开目录 | 交互长尾达标，批量仍持续进展 |
| NET-11 | CPU 忙、磁盘慢、调度停顿 | 不把系统停顿全部误判为网络故障 |
| NET-12 | 多台个人设备同时恢复、若干设备持续离线 | 退避与并发受控，前台不被后台压住 |
| NET-13 | 用户取消、失败重试、写请求、0-RTT | 无隐式重复执行，取消释放资源，原信任门保持 |
| NET-14 | 只用自家中继、暂停、未配对/撤销设备 | 提速不会绕过用户配置或信任边界；长活流的撤销语义单独明确 |
| NET-15 | 长时间闲置与真实手机使用 | 记录空闲流量、唤醒/能耗及恢复体验 |
| NET-16 | 部分可达，只剩一个可达peer；该peer经Relay到目标或第二腿路由缺失/过时 | 保留策略/信任/单跳/总预算与并发上限，自动实际尝试救通；历史Direct、配置存在的Relay和旧失败不能长期压制可用peer relay |

执行分层：每次网络改动的短回归、完整功能矩阵、长时间稳定性与真机。性能对照控制执行器竞争；CPU 忙是单独指定的场景，不能将不受控构建负载混入正常网络结论。执行器不支持的场景标记未验证，不记为通过。

## 8. 开发与证据规范

- 遵守 [REMOTE-DEVELOPMENT.md](../REMOTE-DEVELOPMENT.md)、[LOCAL-CHECKS.md](../LOCAL-CHECKS.md) 及中央 STATE 最新环境约束。本机 source-only，不安装 Node/Rust/Xcode 依赖或执行重型编译测试。U9已授权Turing作为Linux netlab主通道，准确源码/可信driver与原门不变。
- 私库控制入口：`colehank/khor-build`；Mac runner：`khor-mac-mini-m4`；原有任务包括 `fast`、`native`、`lab`；本分支新增网络任务的实际入口见 [ACCEPTANCE.md](ACCEPTANCE.md)。具体可用任务与 runner 状态执行前再查。
- `--task lab` 是原生 KhorLab 构建，不是 Linux netlab。源码快照不自动包含未跟踪/忽略文件，新增源码需先暂存。回执必须匹配被验证的源码 tree。
- Mac 重型任务共享一个槽并经过 `run-build` 资源门；SSH 断线不影响已调度任务。被取消的 pending 不算已检查，不盲目重复提交。
- Linux netlab 已通过私库独立GitHub托管Linux job验证 user namespace、tc、nft/conntrack；现行control/source收据见STATE。未来执行器条件变化时重新预检；不将集群SSH私钥复制到Mac runner。
- 当前中央约定：租机产物不在本机执行；真实 App 验收沿届时获准的现有 Lab/可信构建路径进行。macserver 不持有签名、个人 token、模型或集群凭据。
- 合并需对应提交的可信 GitHub Quality；正式发行由可信 runner 从源码/锁文件重建，不使用租机可执行文件或编译缓存。
- 外部证据：`/Volumes/disk0/Khor/evidence/net/`，各实际 run 的收据与结果见 STATE。原始日志按 run ID 分类，不将机器敏感信息和凭据放进计划。

每份验证收据至少包含：源码基线、candidate commit/tree/dirty 状态、运行 ID/链接、执行器/系统/工具版本、场景和配置/随机种子、负载、样本量/重复次数、原始结果与失败原因、对照版本、结论及未覆盖范围。GitHub artifact 会过期，重要对照数据需及时保存到规范证据目录。
